# flashsale-mini

一个本地生活团购场景的秒杀服务，是《Java 后端开发工程师求职全攻略 (27/28 届)》的配套项目。

它和常见的教程项目做的是同一类业务，但只做两条链路 (商户缓存、秒杀下单)，把**异常流程和一致性**做完整：并发下会不会超卖、消息丢了怎么办、重复消费会不会多下单、Redis 和数据库对不上怎么发现和修复。每个里程碑都有一个可以一条命令复现的对照实验，留下前后对比的数据。

## 里程碑

每个里程碑对应一个 Git 标签，`git checkout m1` 就能看到当时的完整代码，每个标签都能单独运行。

| 标签 | 内容 | 对照实验 |
| - | - | - |
| `m1` | 单体起步：登录 (token 存 Redis，拦截器 + ThreadLocal)、统一返回与全局异常、同步版秒杀的错误写法和正确写法 | 500 个用户每人连点 2 次，抢 100 张券：超卖数、重复订单数 |
| `m2` | 商户详情缓存：旁路缓存、空值缓存防穿透、互斥锁 / 逻辑过期防击穿、过期时间加随机数防雪崩、提交后删缓存、本地缓存 + Redis 两级缓存 | 缓存前后的吞吐；穿透和击穿时打到数据库的请求数；三种更新写法留下旧缓存的比例 |

后续里程碑完成后会追加到这张表里。

## 运行要求

- JDK 21 及以上，Maven 3.9 及以上
- MySQL 8.4 (8.0 也可以)，本机 3306 端口，root 用户无密码 (可以在 `src/main/resources/application.yml` 里修改)
- Redis 7 及以上，本机 6379 端口

## 快速开始

```bash
mysql -u root < sql/schema.sql      # 建库建表
mysql -u root < sql/data.sql        # 1000 个用户 (手机号 13800000001 起)、10 家商户、1 张库存 100 的秒杀券
mvn -DskipTests package
java -jar target/flashsale-mini.jar
```

另开一个终端：

```bash
TOKEN=$(curl -s -X POST 'localhost:8080/user/login?phone=13800000001' | sed 's/.*"data":"\([^"]*\)".*/\1/')
curl -s -X POST localhost:8080/seckill/1 -H "Authorization: $TOKEN"
# {"code":0,"msg":"ok","data":"<订单号>"}
curl -s -X POST localhost:8080/seckill/1 -H "Authorization: $TOKEN"
# {"code":1002,"msg":"不能重复下单","data":null}
```

## m1：同步版秒杀

### 做了什么

- **登录**：按手机号登录 (为了把篇幅留给秒杀，省掉了短信验证码)，生成一个随机 token 存进 Redis，30 分钟过期。登录态放在 Redis 而不是某一台机器的 `HttpSession` 里，以后部署多个实例也能共享。
- **拦截器 + ThreadLocal**：`LoginInterceptor` 从 `Authorization` 头取 token，查出用户 id 放进 `UserHolder` (一个 ThreadLocal)；`afterCompletion` 里一定会 `remove()`，否则线程被下一个请求复用时会读到上一个用户。
- **统一返回与全局异常**：所有接口返回 `{code, msg, data}`；`BizException` 表示可以预期的业务失败 (已抢光、重复下单)，其他异常记日志、给用户一个笼统的提示。
- **订单号**：雪花算法生成，不用数据库自增 (以后分库分表时不会冲突)。
- **两版秒杀** (`SeckillService`)：
  - `naive` (错误写法，接口 `/seckill/naive/{id}`)：先查库存、查这个用户买过没有，在 Java 里判断，再把算好的库存写回、插入订单。订单写进一张没有唯一索引的演示表 `t_voucher_order_naive`；
  - `safe` (正确写法，接口 `/seckill/{id}`)：`UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0` 按影响行数判断是否扣成功；`(user_id, voucher_id)` 唯一索引兜底一人一单，重复下单时整个事务回滚，刚扣的库存也恢复。

### 对照实验

```bash
bash scripts/verify-m1.sh    # 需要先启动 MySQL 和 Redis；MySQL 客户端不在 PATH 里时用 MYSQL=/path/to/mysql 指定
```

500 个用户，每人同时发 2 个请求 (模拟连点)，抢 100 张券。每次实验前重置数据，实验后查库核对。某次运行的结果 (完整输出见 [results/m1.txt](results/m1.txt))：

| 写法 | 订单数 | 下单用户数 | 重复订单 | 超卖 | 剩余库存 | 吞吐 (次/秒) | P99 (ms) |
| - | - | - | - | - | - | - | - |
| 先查后写 (naive) | 645 | 500 | 145 | 545 | 27 | 909 | 1071 |
| 条件更新 + 唯一索引 (safe) | 100 | 100 | 0 | 0 | 0 | 1502 | 628 |

注：Apple M1 Pro，JDK 21.0.10，MySQL 8.4.8，Redis 8.6.2，应用和压测客户端在同一台机器上。每次运行的具体数字不同，但错误写法每次都会超卖几百单、重复下单上百单，正确写法每次都是恰好 100 单。

几个值得看的现象：

- 错误写法卖出了 600 多单，库存却还剩二十几：并发的请求读到同一个库存，各自减一后写回，互相覆盖 (更新丢失)；
- 错误写法里，同一个用户的两个请求同时查到“没买过”，于是都下了单；
- 正确写法不仅数据对，吞吐还更高：它不用先查一遍，一条 UPDATE 就完成了判断和扣减。
- 两种写法的 P99 都在几百毫秒：所有请求都要排队拿数据库连接 (连接池默认 10 个)，并且都在争同一行的锁。这是 m3 把库存预扣挪到 Redis 的原因。

### 简历可以这样写

- 秒杀下单用条件更新 (`stock > 0`) 扣减库存、按影响行数判断结果，`(user_id, voucher_id)` 唯一索引兜底一人一单；压测 500 个用户各连点 2 次抢 100 张券，从“先查后写”的超卖 500 多单降到 0。

### 面试官可能会问

- 先查库存再扣减为什么会超卖？库存为什么会“越卖越多”？
- 条件更新为什么能防超卖？它和 `SELECT ... FOR UPDATE` 有什么区别？
- 一人一单为什么不能只靠代码判断？唯一索引冲突后，已经扣掉的库存怎么办？
- 登录的 token 为什么放 Redis？ThreadLocal 里的用户什么时候清理？不清理会怎样？
- 订单号为什么不用自增 id？

### 扩展方向

- 加上短信验证码登录 (验证码存 Redis，限制发送频率)；
- 用 `SELECT ... FOR UPDATE` 实现第三版，和条件更新比较吞吐；
- 把连接池调大或调小，观察吞吐和 P99 的变化，找到这台机器上的拐点。

## m2：商户详情缓存

### 做了什么

商户详情 (`GET /shop/{id}`) 读多写少，适合缓存。`ShopService` 里有正式接口用的写法，也有几种对照写法，实验接口在 `/lab` 下 (`ShopLabController`)：

| 写法 | 读 | 说明 |
| - | - | - |
| `db` | 直接查数据库 | 对照组 |
| `aside` | 最朴素的旁路缓存 | 查不到的 id 不缓存，热 key 过期时不加保护 |
| `mutex` | 正式接口的写法 | 旁路缓存 + 空值缓存 (防穿透) + 互斥锁 (防击穿) |
| `logical` | 逻辑过期 | key 不设过期时间，过期时间写在 value 里；发现过期的请求抢锁，抢到的交给后台线程重建，所有请求先返回旧数据 |
| `twoLevel` | 两级缓存 | 本地缓存 (Caffeine，5 秒过期) 挡在 Redis 前面 |

- **互斥锁**：`SET lock:shop:{id} <随机值> NX EX 10`，抢到锁的请求查库、写缓存，没抢到的睡 20 ms 再查缓存。释放锁时用 Lua 脚本先比较 value 再删除，避免删掉别人的锁。抢到锁以后**再查一次缓存**：可能别人刚重建完。
- **防雪崩**：缓存过期时间是 30 分钟再加 0–5 分钟的随机数，避免一批同时写入的 key 同时过期。
- **更新**：先更新数据库，**事务提交以后**再删缓存 (`TransactionSynchronization.afterCommit`)；删除失败时在后台重试 3 次，都失败就等过期时间兜底。另外两种写法 (先删缓存再写库、写库后提交前删缓存) 是对照组。

### 对照实验

```bash
bash scripts/verify-m2.sh    # 约 1 分钟
```

真实的商户详情要联表查评分、套餐、营业时间，比主键查询慢得多。实验里用 `SLEEP` 模拟这段耗时 (见 `ShopMapper.findById`)，它和真实的慢查询一样占着一个数据库连接。下面是某次运行的结果 (完整输出见 [results/m2.txt](results/m2.txt))。

**1. 缓存的收益**：64 个并发读同一家商户，3 万次请求。

| 写法 | 吞吐 (次/秒)，查询 0 ms | P99 (ms)，查询 0 ms | 吞吐 (次/秒)，查询 10 ms | P99 (ms)，查询 10 ms |
| - | - | - | - | - |
| 直接查库 | 10281 | 22.7 | 830 | 138.3 |
| Redis | 12020 | 14.4 | 15953 | 9.0 |
| 本地缓存 + Redis | 18588 | 10.2 | 19217 | 9.4 |

只是一次主键查询的话，缓存只快了一点：MySQL 自己的 Buffer Pool 就是一层缓存。查询一旦变重，直接查库的吞吐被连接池卡死 (10 个连接 ÷ 10 ms ≈ 1000 次/秒)，缓存快了将近 20 倍。

**2. 缓存穿透**：反复查一个不存在的商户，1000 次请求。朴素写法查了 1000 次数据库，加了空值缓存只查 1 次。

**3. 缓存击穿**：热 key 刚过期，500 个请求同时到达 (查询 50 ms)。

| 写法 | 打到数据库的查询 | P50 (ms) | P99 (ms) |
| - | - | - | - |
| 不加保护 | 500 | 1419.5 | 2700.0 |
| 互斥锁 | 1 | 148.8 | 198.4 |
| 逻辑过期 | 1 | 125.4 | 172.7 |

不加保护时，500 个请求都去查库，在 10 个连接上排队，P99 到了 2.7 秒。互斥锁和逻辑过期都只查 1 次。两者的区别：互斥锁让大家**等新数据**；逻辑过期让大家**先拿旧数据**，响应快、不会因为重建失败而报错，代价是过期后的一小段时间里返回的是旧值，并且要提前预热。

**4. 更新时的缓存一致性**：8 个线程不停地读，同时改一次价格，改完再读 20 ms，然后核对缓存和数据库。每种写法 100 轮，统计最后缓存里留着旧值的轮数：

| 更新写法 | 事务里没有别的操作 | 事务里还有 20 ms 的其他操作 |
| - | - | - |
| 先删缓存，再写库 | 81 | 100 |
| 写库，提交前删缓存 | 2 | 100 |
| 写库，提交后删缓存 | 0 | 0 |

- 先删缓存：删完到写库提交之间，读请求发现缓存没了，去库里读到旧值，又写回缓存。这个旧值会一直留到过期 (30 分钟)。
- 提交前删缓存：看上去是“先写库再删缓存”，但在事务里删的。删完到提交之间读到的还是旧值 (MVCC 读不到未提交的修改)，同样会写回缓存。事务越长，窗口越大。用 `@Transactional` 时很容易写成这样。
- 提交后删缓存：100 轮里一次也没有。理论上它还剩一个很小的窗口：读请求在提交前读到旧值，在删除之后才写回缓存。要求更高时，可以订阅 binlog (比如 Canal) 来删缓存，或者在删除后延迟一会儿再删一次。

注：Apple M1 Pro，JDK 21.0.10，MySQL 8.4.8，Redis 8.6.2，应用、Redis、MySQL 和压测客户端在同一台机器上。每次运行的数字不同，但结论不变。

### 实现时踩的坑

`ShopService` 有 `@Transactional`，注入到别处的是 CGLIB 生成的代理对象。最初实验接口直接读 `shops.dbQueries` 这个字段，结果是 `null`：代理对象只是一个空壳，它的字段从来没有初始化，方法调用才会转给真正的对象。改成通过方法访问就好了。

### 简历可以这样写

- 商户详情接入 Redis 旁路缓存，空值缓存防穿透、互斥锁防击穿、过期时间加随机数防雪崩，热点数据再加一层 Caffeine 本地缓存；在模拟 10 ms 查询的压测中，吞吐从 830 次/秒提高到约 1.9 万次/秒。
- 热 key 过期时 500 个并发请求打到数据库的查询从 500 次降到 1 次，P99 从 2.7 秒降到 0.2 秒；对比了互斥锁和逻辑过期两种方案的取舍。
- 更新时先写库，事务提交以后再删缓存，删除失败异步重试；用并发读写实验对比了三种写法，“先删缓存再写库”在 100 轮中有 81 轮留下旧缓存，提交后删缓存为 0。

### 面试官可能会问

- 缓存穿透、击穿、雪崩分别是什么？各怎么解决？布隆过滤器和空值缓存怎么选？
- 互斥锁和逻辑过期有什么区别？各适合什么场景？
- 为什么是删缓存而不是更新缓存？为什么先写库再删缓存？这样就完全一致了吗？
- 用 `@Transactional` 时，删缓存应该写在哪里？
- 分布式锁为什么要设过期时间？为什么释放锁要用 Lua？
- 本地缓存和 Redis 的数据不一致怎么办？多个实例的本地缓存怎么同步？

### 扩展方向

- 用布隆过滤器 (Redisson 的 `RBloomFilter`) 替换空值缓存，比较内存占用；
- 用 Redis 的发布订阅，在更新时通知所有实例清掉本地缓存；
- 部署两个实例，观察本地缓存在 5 秒内的不一致；
- 订阅 MySQL binlog 删缓存，把删缓存从业务代码里拿出去。
